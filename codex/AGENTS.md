# AGENTS.md

## 1. 응답 방식

- 모든 대화, 설명, 최종 보고는 한국어로 작성한다.
- 확인한 사실과 가정·추측을 구분하고 간결하게 설명한다.

## 2. 작업 전 판단과 범위

- 관련 코드, 호출 경로, 테스트, 설정을 확인하고 완료를 판단할 검증 방법을 정한 뒤 구현한다.
- 결과를 크게 바꾸는 요구사항이 불명확하면 가능한 해석과 영향을 설명하고 확인을 구한다. 기존 요청으로 판단할 수 있는 세부 구현은 자율적으로 진행한다.
- 유효한 해결책이 여러 개라면 가장 단순하고 기존 코드에 잘 맞는 방법을 선택하고, 중요한 설계 선택에는 성능·확장성·유지보수성의 장단점을 고려한다.
- 요청 해결에 필요한 변경만 한다. 관련 없는 리팩터링·포맷팅·이름 변경은 하지 않고, 이번 변경으로 불필요해진 코드만 제거한다. 범위 밖의 기존 문제는 수정하지 않고 필요한 경우 최종 보고에 언급한다.
- 새 패턴, 추상화, 설정 옵션, 확장 지점, 의존성은 현재 요구사항에 필요할 때만 추가한다. 먼저 기존 코드와 유틸리티로 해결할 수 있는지 확인한다.

## 3. 사람이 리뷰하기 쉬운 코드

- 기존 프로젝트의 스타일과 구조를 따르되, 새로 작성하거나 수정하는 코드에는 아래 가독성 기준을 적용한다. 공개 API나 외부 계약의 이름은 요청 범위 밖에서 바꾸지 않는다.
- 변수·함수·타입 이름은 역할과 도메인 의미를 한 번에 파악할 수 있도록 작성한다. 글자 수를 줄이기 위한 축약어와 `data`, `temp`, `result`, `handle`처럼 대상이나 동작을 알 수 없는 이름은 피한다. 짧은 반복문의 인덱스와 프로젝트에서 통용되는 표준 약어는 허용한다.
- 함수 이름에는 수행하는 동작과 대상을 드러내고, 불리언은 `is`, `has`, `can`, `should` 등 해당 언어의 관례에 맞춰 참·거짓의 의미를 명확히 한다. 단위가 혼동될 수 있는 값은 이름이나 타입에 단위를 표시한다.
- 함수는 하나의 명확한 책임을 갖게 한다. 서로 다른 책임이나 여러 단계의 업무 흐름이 섞이면 의미 있는 이름의 함수로 나누고, 상위 함수에서 전체 흐름을 읽을 수 있게 한다. 줄 수만으로 분리하거나 단순한 표현식을 불필요하게 함수로 감싸지 않는다.
- 깊은 중첩과 복잡한 조건식은 조기 반환, 의미 있는 조건 변수, 책임별 함수로 단순화한다. 읽기 어려운 한 줄 표현보다 명시적인 분기와 중간 변수를 우선한다.
- 입력·반환값·상태 변경·외부 호출이 코드에서 드러나게 한다. 숨은 공유 상태 변경과 실행 순서에 암묵적으로 의존하는 흐름을 피한다.
- 주석은 한국어로 작성하고, 코드만으로 알기 어려운 이유·제약·부작용·호출 순서를 설명한다. 코드의 동작을 반복하는 주석 대신 이름과 구조를 개선한다.

## 4. 구현과 검증

- 동작 변경 전 호출부와 데이터 소비자를 확인한다. 반환값, 오류 처리, 기본값, 저장 형식의 호환성이 달라지면 영향을 명시한다.
- 빈 값, 누락, 중복, 경계 시각, 부분 실패 등 해당 작업에 관련된 예외 상황을 확인한다. 금액·개수·시간 범위처럼 반드시 유지되어야 하는 데이터 조건을 검증한다.
- 오류를 숨기거나 무시하지 않는다. 빈 catch 블록, 의미 없는 예외 처리, 광범위한 예외 포착을 추가하지 않는다.
- 외부 네트워크, DB, 파일 시스템, 운영 리소스 연동은 실패 처리, 타임아웃, 재시도 시 중복 실행의 영향, 관측 가능성을 고려한다.
- 의미가 불분명한 숫자와 문자열은 이름 있는 상수로 표현하되, 의미가 분명한 리터럴까지 과도하게 추상화하지 않는다.
- 코드 생성 도구가 관리하는 파일은 수동으로 수정하지 않는다. 원본 스키마나 생성 설정을 수정한 뒤 재생성한다.
- 버그 수정과 동작 변경에는 변경을 직접 검증하는 집중된 테스트를 추가하거나 수정한다. 단순 문구·스타일 변경이나 구현을 그대로 반복하는 테스트는 불필요하게 추가하지 않는다.
- 변경의 영향과 위험에 맞는 테스트·타입 검사·린트·빌드를 실행한다. 직접 관련된 검증부터 시작하고, 실패나 영향 범위가 더 넓은 검증을 요구할 때 확장한다.
- 실패한 테스트를 삭제하거나 약화해서 통과시키지 않는다.
- 최종 응답 전 diff를 검토해 불필요한 변경을 제거하고, 이름만으로 의도가 드러나는지, 함수의 책임과 데이터 흐름을 쉽게 따라갈 수 있는지 확인한다.

## 5. 운영 작업

- 운영 데이터를 변경하기 전에 환경, 계정, 매장·장치 등의 대상 식별자, 기간과 시간대를 읽기 전용 조회로 확인한다. 가능하면 예상 영향 건수나 dry-run 결과를 먼저 확인한다.
- 대량 변경이나 장시간 작업은 부분 실패 시 진행 상태를 확인하고 안전하게 재개할 수 있도록 한다. 실행 전 복구 방법과 재실행 시 중복 처리 가능성을 확인하고, 가능한 경우 작은 범위에서 검증한 뒤 확대한다.
- 명령 종료 코드나 API 성공 응답만으로 완료를 판단하지 않는다. 변경 후 실제 데이터나 서비스 상태를 확인하고 예상 결과와 비교한다.

## 6. Git, 명령, 보안

- 사용자 변경을 덮어쓰거나 되돌리지 않는다.
- 커밋은 명시적으로 요청받은 경우에만 실행하고, 관련 없는 변경을 포함하지 않는다.
- 커밋 메시지에 `Co-Authored-By` 트레일러를 추가하지 않는다.
- 강제 푸시, 브랜치 삭제, 대량 삭제, 데이터 삭제, DB 마이그레이션, 배포는 명시적 승인 없이 수행하지 않는다.
- `sudo`, 전역 패키지 설치, 시스템 설정 변경처럼 전역 시스템에 영향을 주는 명령은 먼저 허가를 받는다.
- 비밀 정보, 인증 정보, 개인정보를 코드, 로그, 테스트, 문서, 커밋에 노출하지 않는다.
- 인증, 권한, 결제, 개인정보, 데이터 삭제 관련 변경은 보수적으로 검토하고, 안전하지 않은 요청은 위험을 설명한다.

## 7. 문서

- 공개 API, 설정 방법, 사용자 동작이 변경되면 관련 문서를 함께 수정한다.
- 문서는 실제 동작과 검증된 명령 기준으로 작성하고, README나 공식 문서에 있는 내용을 불필요하게 반복하지 않는다.
