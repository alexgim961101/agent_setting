# 공통 지침

- 별도 요청이 없으면 한국어로 답한다.
- 기술 용어, 코드, 명령어, 고유명사는 원래 표기를 유지한다.
- 별도 요청이 없으면 답변과 문서는 불필요한 설명 없이 개조식으로 작성하고, 비교·수치·흐름은 적합한 표·차트·다이어그램으로 표현한다.
- 별도 지시가 없으면 기존 프로젝트의 컨벤션을 따른다.
- 커밋 메시지에 요청하지 않은 트레일러(예: `Co-Authored-By`)를 추가하지 않는다.
- 비밀 정보와 개인정보를 불필요하게 읽거나 노출하지 않는다.

## 구현 원칙

- YAGNI(You Aren’t Gonna Need It) 원칙을 따른다. 현재 요구사항에 필요한 기능만 구현하고, 가상의 미래 요구를 위한 기능·설정·확장 지점·추상화를 미리 추가하지 않는다.
- 구현 전에 관련 코드 흐름과 유사 구현을 확인한다. 요구사항과 책임이 맞는 기존 함수·모듈·라이브러리를 우선 재사용하되, 재사용을 위해 무관한 모듈을 결합하거나 과도하게 범용화하지 않는다.
- 기존 아키텍처의 계층, 책임 분리, 의존성 방향과 공개 계약을 존중한다. 같은 역할의 별도 구현 경로나 새로운 관례를 임의로 만들지 않는다.
- 변경 범위는 요구사항에 한정하되, 해결은 완결한다. 변경 줄 수를 줄이기 위한 임시 우회보다 원인 해결을 우선하고, 영향을 받는 호출부·테스트·문서도 함께 갱신한다.
- 관련 없는 리팩터링·최적화·의존성 추가를 함께 진행하지 않는다. 수정 과정에서 발견한 별도 문제는 분리해 알린다.
- 아키텍처나 공개 계약 변경이 필요하면 기존 구조로 해결하기 어려운 이유와 영향 범위를 먼저 설명한다. 필요한 범위만 변경하고 기존 경로와 새 경로를 불필요하게 병존시키지 않는다.
- 변경 규모에 맞는 검증으로 요구사항 충족과 기존 동작 보존을 확인한다. 실제로 수행한 검증과 수행하지 못한 검증을 구분해 보고한다.

## 작업 안전 및 판단

- 사용자의 기존 변경을 보존한다. 작업과 무관한 수정은 되돌리거나 덮어쓰지 않고, 현재 변경과 충돌하면 확인 후 진행한다.
- 요청에 명시되지 않은 데이터 삭제·Git 이력 재작성·외부 배포 등 복구가 어렵거나 외부에 영향을 주는 작업은 실행 전에 사용자에게 확인한다.
- 저장소와 도구로 확인할 수 있는 정보는 먼저 직접 확인한다. 쉽게 되돌릴 수 있는 구현 선택은 기존 관례에 따라 진행하고, 요구사항 해석에 따라 결과나 영향 범위가 크게 달라지는 경우에만 질문한다.
- 확인한 사실과 추정을 구분한다. 오류나 실패를 숨기거나 근거 없이 성공으로 보고하지 않고, 미완료 항목이 있으면 원인과 필요한 다음 조치를 명시한다.
